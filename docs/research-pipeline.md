# 競馬ナイン：買い目と時系列検証の準備

この段階は架空データ専用です。研究用の `simulate` は購入推奨ではありません。
実データ・JRDB接続・ブラウザーの公開予想への接続はまだ有効にしていません。
料金の発生するAPI呼び出し、データの自動保存、外部送信もありません。

## 処理の流れ

1. `research_snapshot_guard.audit_research_snapshot`：架空の根拠と発走前の時刻を検査し、予想入力の照合用SHA-256を作成。
2. `evaluation_policy.evaluate_race`：10項目の根拠と予想時点を確認。
3. `research_planner.plan_race`：根拠の時刻検査を通過したものだけで勝ち切る候補、相手、最大40点を組み立て。
4. `research_backtest.backtest`：固定した予想・根拠入力のハッシュを残し、別入力の結果と照合。

全段階が `recordType: test` 限定です。出力は draft / validated=false /
publishable=false。結果の数字が良くても、このフラグは自動変更されません。

## 予想締切前の根拠チェック（追加）

- 架空の予想入力だけに適用し、実戦・有料JRDBデータやレース結果を研究入力として渡すことを拒否。
- 各根拠の `availableAt` が `asOf`（予想時点）より後なら、**他に十分な根拠があっても**買い目生成前に停止する。発走後の着順、払戻などを混入させた入力も停止。
- 全頭の10項目を確認し、資料のない項目は未確認のまま（勝手に評価を付けない）。レース日・発走時刻の整合性、同一項目の重複資料も検査。
- `snapshotSha256` は発走前の根拠入力を一定順で並べた検証用指紋。並び順だけ変わっても一致し、評価内容や `asOf` を変更したら変わる。検証レポートにも保持する。
- **重要：ハッシュだけで「本当に発走前に取得・保存した」「提供元が公式」「結果を知らずに予想した」と証明できるわけではない。** その証明や実戦収支の集計には、取得時刻を独立して固定する非公開の保存先と、正規データの接続が別途必要。
- iPhoneの架空研究画面では詳細欄に先頭12桁の指紋と自己申告日時の注意を表示。S/A/B/Cの既存色、架空8頭・36点の参考表示、購入や正式記録とは分離したまま。

## 見送り・保留・検証対象

| 状態 | 研究処理 |
|---|---|
| 重要な評価が未取得・懸念が未確認 | 保留 |
| 勝ち切る根拠のある候補が0頭 | 見送り |
| 候補が4頭以上 | 保留・全候補を再検討 |
| 候補が1頭だが十分な優位がない | 保留 |
| 1〜3頭の候補と相手が揃う | 架空検証用の買い目を生成 |

1頭固定は、総合S・3項目以上の勝ち切る根拠・次点とのスコア差0.5以上を
仮条件にしています。これは検証前の仮説であり、強い軸を保証する数値ではありません。

## 点数配分

- 1着：評価処理で再検討対象になった1〜3頭をすべて残す。
- 2着：総合S/A、または勝ち切る根拠で選ばれた候補。
- 3着：総合S/A/B、または勝ち切る根拠で選ばれた候補。
- 根拠付きの重大な懸念がある馬は、相手にも自動採用しない。
- 1頭の馬が同じ買い目の複数着順に重複する組み合わせは除く。
- 合計40点まで。1着候補ごとに上限を均等配分する。
- 相手候補は仮の優先度「2着スコア×2＋3着スコア」で整理する。
- 上限の境界で同評価になった組み合わせは、馬番順で恣意的に切らない。
  同評価のまとまりをすべて入れられない場合、そのまとまり以下を採用しない。
- 1着候補のどれかが0点になるなら、勝手に軸を減らさずレース全体を保留。
- 30点に届かなくても弱い候補を足さない。1点100円で計算する。

この配分は確率・期待値の最適化ではありません。実データで検証してから見直します。

## 時系列での検証

`backtest(races, outcomes, split_at)` は予想の入力と結果を別に受け取ります。
レースごとの評価・買い目を先に作り、ハッシュを残してから結果を参照します。
結果を差し替えても予想や買い目が変わらないことをテストしています。

`split_at` より前を development、以後を validation として別集計します。
予想作成から発走までが境界をまたぐ場合は拒否。境界は開催間に設定してください。
この処理は学習や自動最適化を行いません。人が検証期間を見てルールを修正した場合、
その期間は未使用検証期間ではなくなるため、新たな期間で確かめる必要があります。

集計するもの：

- 対象レース数、保留・見送り数、購入想定レース数、結果確定数
- 全買い目の購入想定額、払戻、収支、回収率
- 結果待ちの購入想定額、中止で返還された購入想定額
- 最大連続赤字レース数、累積収支のピークからの最大下落額

結果待ちは赤字として数えません。中止は全額返還として別記し、的中率・回収率の
母数から除外します。同着・出走取消の個別返還には未対応のため、明示的に拒否します。
複数の予想版を別レースとして二重計上しないよう、レースIDと開催日・場・Rの重複を拒否します。
同時刻のレースはレースID順で表示するため、最大下落額もその順の計算です。

```sh
python -m unittest discover -s tests -p 'test_*.py'
```

上記コマンドで、時刻リーク・結果混入・指紋再現性・欠損の単体テストも含む全テストを確認します。
買い目を構成する根拠を生のJRDB項目から生成する処理と、本人だけの非公開環境は
別途必要です。現時点で実際の予想精度や回収率が検証できたわけではありません。

## 本人用：1着候補・回収率の時系列振り返り画面（2026-11-05）

- `/research-validation-demo` にログイン済み本人だけが開ける**2099年の架空72レース**の研究画面を追加。公開GitHub Pagesや購入画面には実績として掲載しません。
- 架空の初日36Rを開発用、翌日36Rを検証用として、**境界を予想・結果の照合より前に固定**します。結果待ちと中止を除いた架空の確定結果は各日30Rです。
- `research_backtest.backtest` と `research_winner_diagnostics.audit_synthetic_winners` を再利用し、総合1〜3位以内の勝ち馬、勝ち切り再検討候補にいた馬、1着馬券から漏れた馬、3連単的中、架空投資・払戻・回収率を別々に確認。
- 入力資料の `snapshotSha256` により、結果を変更しても予想入力の指紋が変わらないことをテスト。ただし**発走前に実際に取得されたことを外部から保証するものではない**。
- 架空の払戻や勝ち馬は動作確認用に恣意的に作ったもの。表示された回収率、的中率、勝ち馬順位の分布は**実際の予想性能を一切示しません**。その数字で評価の重みを調整したら、未使用の別期間で再検証する必要があります。

今後、**実戦採用の前に必要な検証ゲート**は、(1) JRDB契約上の利用許諾・認証、(2) 独立したJRA公式出走/取消/馬場/時刻照合、(3) 出馬表と根拠データのID・取得時刻を非公開環境で固定、(4) 根拠つき全10項目評価と欠損処理、(5) 予想版を固定した未使用期間の結果検証、(6) 同着・返還・取消を含む実際の払戻精算、(7) 個人向け表示と一般公開の利用条件を分離、の順に行うこと。

どれも今回の架空テストだけでは解除できません。実データや認証情報が入るまでは、実戦予想生成・自動購入・記録混在を許可しません。
