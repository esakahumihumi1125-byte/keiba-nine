# 競馬ナイン本人用：10項目の資料確認（2026-11-09）

## 現在の実装範囲

**予想完成ではなく、資料・仮説・確定評価の区別をする機能。**

- 重みは調教30、近走3、コース距離20、展開20、馬場12、血統8、枠斤量3、騎手厩舎2、ローテ1、馬体重1＝100点。S85点〜、A70点〜、B55点〜、Cは55点未満。完成判定は発走前の根拠付き**全10項目**が必要。
- `scripts/jrdb_five_factor_hypotheses.py` は、既存の調教/近走の**暫定**ランクと、同条件の好走実績・過去4角の位置取りから計算した**研究用**の目安を1頭の5スロットに統合する。適性・展開の本採点ではない。
- `scripts/jrdb_ten_factor_source_inventory.py` は、既存の本人専用 /tky・/tze 由来資料と上記5スロットを同じレース・馬番で照合する。残り5項目については、父・母父、枠・負担重量、騎手・調教師、前走からの間隔、馬体形状コードの資料有無のみ確認。**馬体形状コードは当日の馬体重ではない。**
- `scripts/jrdb_history_pipeline.py` の上限付き過去履歴の応答に `fiveFactorHypotheses` と `tenFactorSourceInventory` を追加。新しいJRDBリクエストは増えない。履歴API自体は本人の任意操作・利用設定が必要。
- `scripts/owner_auto_forecast_ui.py` は、本人用 `/owner-auto-forecast` で「過去の同条件を最大8件照合する」を押した場合に、10項目の研究用資料状態を馬番ごとに展開表示。元の有料馬名、指数、認証キー、馬ID、レースキー、馬体重の原数値はレスポンスへ複製しない。
- 同じ画面の「今日の馬体重資料を確認」は、従来の `GET /api/jrdb/prestart-body?date=YYYYMMDD` をユーザーが押した時だけ呼ぶ。/tra・/tky・/tpdの3リクエストをサーバーが行い、**体重・前走比の有無（件数）だけ**を表示する。取得は `JRDB_PRIVATE_ENABLED=1` と `KEIBA_PRESTART_BODY_ENABLED=1` と本人認証の条件を満たす時のみ。日本時間当日以外はサーバーがAPIアクセス前に拒否する。古い端末時刻に依存しない。
- APIの生レスポンスやオッズは公開JSON、GitHub Pages、買い目、記録、仮想収支に流さない。

## 本人用全R画面：当日データの進捗パスポート（2026-11-09）

- `scripts/owner_day_source_passport.py` が、すでに1回取得した番組・出走馬・調教・近走（4種類）と任意の当日馬場情報、観測用の既存資料件数を**同一要求内で突合**する。追加の有料JRDB APIアクセスは0回。
- 各レースに「仮評価の調教・近走の頭数」「父・母父／枠斤量／騎手厩舎／ローテ／馬体形状／過去4角の観測件数」「コース情報と馬場情報の有無」をまとめる。観測元の馬名・馬ID・レースキー・指数・斤量の値は公開しない。
- `/owner-auto-forecast` の各レースを開くと、**「10項目の資料進捗（正式採点0/10）」**を選択して確認できる。前日・当日資料が足りないときも0件と誤表示せず照合保留とする。
- 10項目の重みと分類は変更なし。調教・近走もあくまで仮評価、残り8項目は正式未評価。過去の位置取り観測を展開予測、馬体形状を当日の馬体重、コース情報の存在を適性S評価として扱わない。
- 暫定予想が発走前に固定済みなら、その記録は**追記・変更しない**。この表示は情報の進捗のみで、新しい三連単や購入シグナルを生成しない。
- `/api/jrdb/connection-test` の本人操作による結果について、Renderの非公開アプリログには固定文字列の接続成否だけを出す。**開催日・有料データ・認証キー・馬情報・原件数はログに出さない**。本人の操作がなければテスト用のAPI通信も行わない。

## 独立した根拠に基づく穴馬1着の代替案（2026-11-09）

`scripts/owner_full_ten_factor.py` の入力が独立したJRA公式4点確認、10項目すべての発走前の根拠、本人側の評価検証を満たした場合に限り、`scripts/owner_upset_alternative.py` が別案を作成する。

- 総合4〜6位のうち、調教・距離適性・展開という**異なる項目**でS/Aと勝ち切り根拠があり、さらに**異なる出所の記録**が2種類以上ある馬だけを対象とする。同じ資料からの二重計上はしない。
- 勝ち切り候補が複数ある場合や順位が同点で決められない場合は、勝手に1頭を選ばず見送りにする。
- 基本の3連単フォーメーションは**そのまま保持**。穴馬1着案は別の30〜40点（やむを得ない少点数も許容）で表示するためのデータ構造だけ。**基本案＋別案を合算して購入する仕様ではない**。どちらかを本人が選ぶ必要がある。
- 同点境界を馬番で恣意的に分けない。48点超の組み合わせは除外。全条件が未検証なら代替案も0点。オッズ・人気・結果を参照せず、後付けで買い目を編集しない。
- このモジュールは単体の合成テストで動作確認できるが、まだ実データを使った本人用の本予想フローには接続していない。これを実戦投入可能、予想精度・回収率改善済みと解釈しない。

## 本予想につながる未完成事項

1. 同じコース・距離・馬場における能力と血統の比較モデルを、根拠付き・事前固定の評価基準で確立する。過去好走率の目安を「勝てる確率」に読み替えない。
2. 展開・脚質をレース全体の位置取りや先行圧力から推定し、検証可能な採点法へ引き上げる。過去4角の件数だけでは不十分。
3. 枠・斤量の利不利、騎手/厩舎成績、ローテ別適性、**実際の当日馬体重変化**に基づく採点を確立する。資料がなければ未評価にする。
4. JRA公式の出走馬・取消・馬場・発走時刻の独立照合（表示資料の自己申告だけでは不可）。
5. 発走前に完全評価がそろったレースのみ本予想を固定し、3連単候補を30〜40点中心／最大48点で提示する。公式結果と照合して100円仮想収支を自動集計する。実購入には接続しない。

**現状は正式採点0/10・JRA公式独立照合なし。** データの存在件数が一致しても本予想は生成しない。すでに署名・保存した研究用買い目は後付けで上書きしない。

## iPhoneの発走前記録のサーバー署名検証（2026-11-09）

- 本人用自動予想画面の「発走前に固定した買い目の履歴」から「この日の固定買い目をサーバーで署名確認」を本人が押した時だけ、**その日の既存端末記録だけ**を `POST /api/owner-100yen-verify-receipts` に送る。
- これは既存の本人認証と署名検証ルートを再利用し、新しいJRDB API通信・予想生成・保存・購入・公式結果の取得は行わない。署名が正しければ検証件数を表示し、結果はすべて未確認のまま収支には加えない。
- 署名が合わない・パスワード変更などで古い記録を検証できない・記録の形式がおかしい場合は、サーバー保存済みや的中したと表示しない。**古い買い目は削除・改変しない**。端末バックアップと設定を確認する。
- iPhoneの開催日を切り替えた場合、以前の遅い検証結果は無視する。送信するJSONは日付と本人用の固定研究記録だけで、原JRDBレスポンス、APIキー、馬名、オッズを含まない。
- **サーバー署名の成功はサーバーへの永続保存を意味しない。** Renderの本人用環境にはPostgres未作成のため、`KEIBA_OWNER_RECEIPT_ARCHIVE_ENABLED` は有効にしていない。端末記録の保全には本人用バックアップ画面を使用。JRAの公式確認・予想の正確さ・実購入・的中・回収率も一切保証しない。
