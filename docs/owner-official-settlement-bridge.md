## 2026-11-10：結果照合・複数払戻の計算核を追加

現状、**JRA公式の確定結果を自動取得して認証する通信アダプターは未接続**です。本人用の既存APIが返す正式回収率は引き続き「未確認」のままです。今回作った \`scripts/owner_official_settlement_replay.py\` は、**完成版で公式結果を接続した後**に必要になる、署名済み発走前買い目と複数払戻・返還を突合する研究用の独立計算核です。

### 結果の真正性と予想の固定は別物

- **予想側**：\`owner_prestart_receipt.verify_preview_receipts()\` が検証済みの署名・固定時刻・馬番・重複なしの3連単／3連複だけを対象とする。発走後に買い目を書き換えたり再発行しない。
- **結果側**：将来実装する **JRA公式ページの独立した取得・認証アダプター** だけが、出典・日付・競馬場・レース・確定払戻を検証してから、本人サービス内の別秘密鍵で正規化済み結果にHMAC署名する設計。結果署名用鍵はログインパスワードや発走前予想の署名鍵と分離する。
- このモジュール内の \`sign_authenticated_source_record()\` は**内部アダプター専用の機能**で、単に公式URL文字列を渡すだけでは原本の真正性を証明しない。**本人向けHTTPエンドポイントには公開しない**。結果の受信・署名をユーザーのブラウザーから行わない。結果HMACを信頼できても、独立したJRA取得自体は未完成。
- 予想の締切・結果公開時刻・照合を要求。本人用サーバー時計より未来の結果、発走前に確定したと称する結果、別開催日・別競馬場・R・重複・不正署名は拒否。入力レコードを変更せず、秘密鍵やJRDB原本、馬名、URLをレスポンスへ返さない。

### 1点100円の集計

- 3連単と3連複の**的中組み合わせごとの100円払戻**を独立して集計する。3着同着などで3連単の払戻組み合わせが複数あっても、元の**買っていた点数だけ**該当分を足す。勝ち馬の人気・オッズで後から購入点数を変えない。
- 返還対象の馬券があれば各100円を払戻に含める。競走自体が取りやめの場合は、固定した全買い目を100円ずつ返還として計算する。実購入に関する証明ではない。
- JRA独立結果が確認できないレース、当日署名済みの買い目が存在しないレースは**pending**。0円払戻や不的中に置き換えない。確認済み・保留のレースを混ぜて誤った回収率を出さない。
- テスト用の \`replayRoiPercent\` を正式な回収率へ昇格させない。**\`officialRoiPercent = null\`、\`officialJraVerified = false\` が現段階の固定値**。既存の予想履歴、購入記録、仮想収支、固定署名は一切上書きしない。
- JRA 2026-11-08 京都8Rのような3着同着で2種類の3連単払戻が発生するケースを検討対象にする。合成テストは2099年の仮架空レースで支払パターンのみ再現し、過去の公式結果を後付けの競馬予想として使用しない。

### 残る必須工程

1. JRA公式ページの出典/版/当日確定状況を認証する独立通信アダプター。出走取消・同着・払い戻しの一意な正規化。
2. 発走前に固定された予想を、本人専用の長期永続Postgres等へ**明示的な承認後**に保存し、結果側との監査可能な紐付けを完成する。現行Renderの一時ファイルをDB代替にしない。
3. 元となる10項目採点をJRDB実資料とJRA公式出走・時刻照合で検証し、未来の結果が混ざらない時系列バックテストを実施。調教30・近走3・コース距離17・展開脚質17・馬場12・血統6・枠斤量3・騎手厩舎10・ローテ1・当日馬体重1を根拠付きで整備する。
4. 単なる研究用シミュレーションと正式に確認済みの100円仮想収支、実購入の記録を引き続き別々に管理する。
